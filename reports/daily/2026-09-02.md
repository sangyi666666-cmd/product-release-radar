# 企业级 Agent / AI Worker / DataAgent 行业雷达

日期：2026-09-02  
类型：增量日报  
观察窗口：2026-08-31 10:45 至 2026-09-02 10:45（北京时间）

## 今日结论

今天最重要的变化不是 Agent 又多了几个工具，而是企业平台开始明确“工具无权限时怎么办”。Snowflake 计划让 Agent 在部分工具无权限时使用剩余工具继续执行并返回结构化警告；AWS 的高风险支付案例则把信任检查设计成模型无法绕过的确定性门禁。

两者并不矛盾，而是在形成一套风险分级原则：低风险、可解释的分析任务可以最小权限降级；涉及付款、数据写入、账号变更等不可逆动作必须失败关闭。平台需要把这种策略做成产品配置，而不是散落在 Prompt 或业务代码里。

另一个清晰趋势是控制面从单一聊天入口扩展到 Registry、移动端和工作入口：AWS Agent Registry 管理 Agent、工具和 Skill 的发现与生命周期；ChatGPT iOS 强化跨主机任务接续；AgentCore Runtime 托管的 MCP 服务可以通过身份链进入 Amazon Quick。

火山引擎 AgentKit、豆包工作、QoderWake 等重点产品在本窗口未发现新的高价值 P0 发布。Qoder 与 Kimi Work 有小版本更新，记录在对应栏目，不占用 Top 5。

## Top 5 Signals

### 1. Snowflake 开始把“部分工具无权限”从整次失败改为降级执行

**可验证事实**：Snowflake 的行为变更公告计划从 9 月 2 日开始：当调用者角色无法访问 Agent 配置中的部分 Cortex Search、Cortex Analyst、MCP 或 Skill 工具时，Cortex Agents 与 Snowflake CoWork 不再因首个无权限工具返回 HTTP 4XX 并终止整次运行，而是使用可访问工具继续执行，返回 HTTP 200，并通过 `response.warning` 报告不可访问工具。公告同时注明计划日期可能变化，渐进发布预计到 11 月 18 日完成。[Snowflake 官方公告](https://docs.snowflake.com/en/release-notes/bcr-bundles/un-bundled/bcr-2425)

**产品判断**：这是 Agent 权限模型从“配置期静态校验”走向“运行期能力裁剪”。同一个 Agent 面对不同角色会形成不同的可用工具集，任务成功不再等于使用了完整数据和能力。

**启示**：DataAgent 需要同时表达“答案是否生成”和“答案覆盖是否完整”。如果缺失薪酬、预算或敏感明细工具后仍能返回结论，前端必须展示缺失能力、影响范围和结论限制，不能把警告藏在流式事件或日志中。

**建议动作**：把每个 Tool 标记为 `必需 / 可选 / 可替代`，为无权限场景配置 `阻断 / 降级 / 请求授权 / 转人工`，并把“本次未使用哪些数据和工具”纳入答案引用区。

### 2. AWS Agent Registry GA，Agent、MCP、Skill 开始进入统一资产生命周期

**可验证事实**：AWS 8 月 31 日宣布 Agent Registry 正式可用，用于统一登记、发现和治理 Agent、MCP、Skill 及自定义资源。官方设计区分 Governance Plane 与 Discovery Plane：前者保存完整资产及合规、权限和生命周期元数据，后者只向消费者暴露已批准资源，并支持语义与关键词检索。Registry 支持审批状态流转，操作写入 CloudTrail 审计记录。[AWS 官方发布](https://aws.amazon.com/blogs/machine-learning/manage-agents-tools-and-skills-at-scale-with-aws-agent-registry/)

**产品判断**：企业 Agent 平台的竞争对象正从“谁的 Builder 更好用”升级为“谁能成为 Agent 资产的 System of Record”。Registry 的核心价值不是应用市场，而是回答谁创建、谁负责、哪个版本、审核到哪一步、谁有权发现和调用。

**启示**：Agent、Tool、Skill 不能只存在于项目配置和运行时数据库中。它们需要统一 ID、Owner、版本、数据分类、风险等级、适用场景、评测状态、批准范围、依赖和退役日期。

**建议动作**：先设计一张最小 Registry 元数据表，选择 3 个 Agent、5 个 Tool、3 个 Skill 做人工登记，验证是否能完成发现、审批、版本追溯、影响分析和下线五个动作。

### 3. t54 披露超过 2,000 万次无人工逐笔审批的 Agent 微支付

**可验证事实**：AWS 9 月 1 日发布的客户案例称，t54 的 x402-secure 与 AgentCore payments 已处理超过 2,000 万次 Agent 发起的交易，单笔为 0.001～0.01 美元，无需人工逐笔审批。其架构使用会话级消费上限、凭证隔离、IAM 职责分离和支付前的确定性信任门禁；Agent 可以执行支付，但不能修改自身额度、创建钱包或读取原始凭证。[AWS 官方客户案例](https://aws.amazon.com/blogs/machine-learning/how-t54-built-a-trust-layer-with-amazon-bedrock-agentcore-payments/)

**产品判断**：这个案例的重要性不在加密支付，而在证明“无人逐笔审批”不等于“无治理”。可规模化自治依赖预算、身份、对手方风险、职责分离和审计同时成立。

**启示**：财务类数字员工的自治等级不应只按任务名称配置。审批策略至少要同时考虑金额、累计预算、收款对象、数据可信度、可逆性、异常频率和用户角色。

**建议动作**：用报销、付款申请或预算调整中的一个场景，建立 `动作—风险—确定性门禁—人工审批—额度—审计证据` 六列表。模型只能提出动作，不能修改门禁和额度。

### 4. ChatGPT iOS 把手机进一步变成跨主机长任务控制面

**可验证事实**：9 月 1 日的 ChatGPT iOS 1.2026.237 支持附件跨已连接主机使用；新增 Priority 视图集中显示运行中、未读和等待响应的任务；排队 Prompt 可与连接主机同步、编辑并在应用进入后台时发送；长任务开始显示实时工作时长。[OpenAI 官方 Changelog](https://learn.chatgpt.com/docs/changelog)

**产品判断**：移动端的价值不是复制桌面对话，而是成为长任务的轻量控制塔：查看状态、补充输入、处理等待事项和接管异常，实际执行仍由连接主机或云环境完成。

**启示**：数字员工应把“执行环境”和“控制入口”解耦。同一任务可以在云端或受控工作站运行，而用户在 IM、Web 或手机上完成授权、纠偏和验收。

**建议动作**：画出一次跨端任务的状态同步图，至少覆盖任务 ID、执行主机、排队输入、未读更新、待审批、断线重连和最终产物，检查是否存在入口切换后状态丢失或重复执行。

### 5. AgentCore 托管 MCP 服务可以复用到 Amazon Quick 工作入口

**可验证事实**：AWS 8 月 31 日发布了 AgentCore Runtime 托管 MCP Server 接入 Amazon Quick 的官方方案。方案通过 Quick Connector 与 AgentCore Gateway 连接；入站身份用于授权用户访问 MCP 服务，出站身份用于 Gateway 到 Runtime 的机器身份认证。相比直接 REST 或 Lambda，Runtime 方案提供会话隔离、长执行时间、持久文件系统、认证、可观测、双向流和评测。[AWS 官方方案](https://aws.amazon.com/blogs/machine-learning/connect-an-agentcore-runtime-hosted-mcp-server-to-amazon-quick/)

**产品判断**：MCP 正从开发者工具协议变成“平台能力到工作入口”的复用边界。真正难点不是暴露一个工具描述，而是让用户身份、Agent 身份和服务身份沿调用链连续传递。

**启示**：DataAgent 能力应同时支持人用产品入口和 Agent 用工具入口，但两者应复用同一语义层、权限、评测和审计，不应分别实现两套业务逻辑。

**建议动作**：为一个只读问数能力设计双入口：聊天页面与 MCP Tool。明确用户身份如何传入、行列权限在哪里执行、引用和 Trace 如何统一、哪个组件对结果负责。

## Agent 开发平台

今天的平台信号集中在三个控制面对象：

```text
Registry：什么能力存在，谁负责，谁能发现和使用
Runtime：任务在哪运行，如何隔离、恢复和观测
Policy：本次动作允许、降级、待审批还是阻断
```

AWS 同时补齐 Registry 与工作入口集成，说明企业级平台正在把开发、发布、发现、调用和审计串成一个生命周期。

OpenAI 9 月 1 日另发布 Codex CLI 0.152.1，修复 Guardian 审批审查未遵循模型元数据中 Node REPL 策略的问题。该补丁很小，但再次说明权限策略必须在所有执行入口保持一致，不能出现 TUI、REPL、工具调用各自解释策略的情况。[OpenAI 官方 Changelog](https://learn.chatgpt.com/docs/changelog)

火山引擎 AgentKit / VeADK 在本观察窗口未发现新的正式版本或高价值 P0 公告，继续固定跟踪动态 Harness、Runtime、MCP/API 网关、身份权限、沙箱、记忆/知识、评测和运营分析，不重复昨天的产品基线。

## 数字员工 / AI Worker

ChatGPT iOS 的跨主机任务同步表明，数字员工入口正在从“人守着桌面等结果”转为“任务持续运行，人通过任意入口管理例外”。移动端最重要的页面不是聊天记录，而是运行中、待确认、已完成和异常任务队列。

Claude Cowork 官方企业说明近期补充了内置浏览器和云端执行的组织级控制：Team 的云端运行默认开启，Enterprise 默认关闭并通过自定义角色授权；内置浏览器在 Team 本周逐步默认开启，Enterprise 计划 9 月 10 日默认开启，管理员可以提前关闭。自动批准模式也由组织设置控制。[Anthropic 官方说明](https://support.claude.com/en/articles/13455879-use-claude-cowork-on-team-and-enterprise-plans)

**产品判断**：工作 Agent 的默认权限本身就是企业上线事件。管理员需要清楚知道某个版本后哪些能力从关闭变为开启，以及这会扩大哪些浏览器、文件和云端执行边界。

## DataAgent

Snowflake 今天的权限降级行为是本赛道最重要的增量。它带来一个新的准确性风险：任务技术上“成功”，但数据覆盖不完整。DataAgent 的评价指标应把 `完整能力下正确率` 与 `权限受限下的安全降级率` 分开。

建议新增四类权限测试：

1. 缺失必需数据工具时必须拒答；
2. 缺失可选工具时可以降级但必须说明影响；
3. 存在替代工具时记录选择理由和口径差异；
4. 角色权限变化后，历史会话不得继续复用已撤销能力。

Databricks Genie、Microsoft Fabric Data Agent、Google Conversational Analytics 在本窗口未发现足够强的新 P0 正式发布，不重复既有基线。

## 企业案例

t54 的案例说明，高频财务动作无法依靠人工逐笔审批扩展，但可以通过多层控制实现自治：

```text
模型提出动作
→ 确定性风险门禁检查对手方
→ 身份系统提供短期凭证
→ 预算系统检查会话额度
→ 支付执行
→ 全链路审计
```

需要注意，2,000 万次交易及效果数据来自厂商客户案例，不能等同于独立审计结果。可借鉴的是控制结构，而不是直接套用规模和 ROI。

## 风险与反信号

- 降级执行如果只返回技术警告而不进入用户界面，会制造“答案完整”的错觉；
- 被登记到 Registry 不等于已安全可用，审批、评测和运行策略必须真实联动；
- 高风险动作不能让模型自行判断是否跳过安全检查，门禁必须独立、确定且不可被 Agent 修改；
- 浏览器或自动批准能力默认开启会扩大组织风险面，管理员需要版本变更预警和影响清单；
- 多个小版本都在修复睡眠、后台和进程状态，反向说明长任务的设备连续性仍未完全成熟；
- 厂商客户案例中的规模和收益数据未经独立核验，只作为架构线索。

## 今日建议深挖

今天完成一个 60 分钟实践：设计“权限受限时的 DataAgent 降级规范”。

```text
用户问题：
可能使用的 Tool：
每个 Tool：必需 / 可选 / 可替代
缺失原因：无权限 / 不可用 / 超时 / 超预算
系统动作：阻断 / 降级 / 请求授权 / 转人工
对答案覆盖与口径的影响：
用户可见警告：
日志与审计事件：
回归测试用例：
```

验收标准：选择一个 HR 或财务问题，分别模拟完整权限、缺少可选工具、缺少必需工具三种情况；用户能准确判断答案是否完整，系统不会因为 HTTP 200 就把降级结果计为完整成功。
