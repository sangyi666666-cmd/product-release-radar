# 企业级 Agent / AI Worker / DataAgent 行业雷达

日期：2026-09-15

## 今日结论

本窗口有两条高价值增量，指向同一个更具体的工程问题：**当 Agent 系统把模型、成本与延迟的取舍交给自动路由后，企业仍要保留可解释的任务级控制与验收证据。**

GitHub Copilot 于 9 月 14 日为 Auto model selection 新增“效率、平衡、智能”三档偏好，并开始向 VS Code、Copilot CLI 与 Copilot app 滚动。三档使用同一可用模型集合，路由仍会按每个 prompt 选择模型，且按实际选中模型计费；它不是固定模型套餐，也不是在每个任务上保证质量/延迟/成本的 SLA。OpenAI 同日发布 Perplexity 的 Astra 使用案例：其称已用于编写沟通内容、修改软件和监测生产系统，并让模型生成测试程序模拟外部服务、检验端到端流程。这是有价值的客户一手实践，但没有披露完成率、事故率、成本或独立对照，不能外推为“可少审查”或一般性 ROI。

因此，今日的关键不在于再加一个“智能档位”，而在于将自动路由变成可运营能力：每一次高风险任务都应能回看实际模型/快照、路由档位、工具与权限、成本、测试证据、人工介入和最终业务结果。若这些记录缺失，成本优化会掩盖模型行为变化，端到端“信任”也会退化为不可审计的主观判断。

## Top 5

### 1. GitHub Copilot Auto model selection 新增效率、平衡、智能三档偏好｜82 分

**可验证事实**：GitHub 于 2026 年 9 月 14 日宣布，Copilot Auto model selection 提供 efficiency、balance、intelligence 三档：前者优先低成本，后两者分别权衡成本/质量/响应时间和优先复杂任务质量。三档使用同一组可用模型；Auto 仍按每个 prompt 选择其认为合适的模型，例如即使选择 intelligence，简单 docstring 任务仍可能被路由到较小模型。该功能正在向 VS Code、Copilot CLI 与 GitHub Copilot app 滚动；按 Auto 实际选中的模型计费，付费订阅用户经 Auto 计费继续享有 10% 折扣。[GitHub Changelog](https://github.blog/changelog/2026-09-14-configure-cost-and-quality-in-copilot-auto-model-selection/)

**产品判断**：这是把“选模型”从一次性管理员配置变成任务级路由偏好的一步，且覆盖 IDE、CLI 与应用入口。它有助于把常规、复杂和成本敏感任务放到不同优化目标下；但用户选择的是目标权重而非确定模型，模型集合、路由逻辑、实际延迟、工具表现与账单仍可能随 prompt 变化。正在滚动的状态也意味着不同账户、入口与地区不应被默认视为已一致可用。

**启示**：模型路由控制面至少需要两层记录：策略层保留用户/组织选择的档位、模型可用池与生效范围；执行层保留每一次请求的实际模型或快照、reasoning/工具配置、缓存与 token/调用成本、延迟、失败/重试以及任务验收结果。否则无法判断“节省”来自任务更简单、路由更便宜，还是质量被转移给后续人工返工。

**建议动作**：选择 30—50 个具有既定验收标准的代表任务，按敏感度分组：低风险文本/检索、代码修改、涉及外部副作用的操作。分别跑三档并固定相同上下文、工具权限与人工审核门槛；比较任务成功率、返工、P95 时延、实际成本、工具拒绝和人工介入，而不只比较会话数或模型名称。将最小质量阈值与异常回退（固定模型、人工接管或停止）写入策略。

### 2. OpenAI 公开 Perplexity 的 Astra 端到端测试与生产监测实践｜68 分

**可验证事实**：OpenAI 于 2026 年 9 月 14 日发布客户案例，称 Perplexity 使用 GPT-6 Astra 编写沟通内容、修改软件并监测生产系统。案例还描述了一个测试方式：让模型围绕应用生成小型测试程序，模拟语言模型 API 或 connector 等外部服务响应，以检查应用的端到端行为；Perplexity 高管称其比早期模型更少需要人工查看。[OpenAI 客户案例](https://openai.com/index/perplexity-improving-accuracy-with-astra/)

**产品判断**：这不是一份独立评测，也没有证明模型能在无监督条件下稳定修改任意生产系统。它的价值在于公开展示了 Agentic Coding 的产物从“代码变更”向“测试程序、模拟依赖、运行证据和未覆盖范围”扩展；高管的信任与查看频率是客户口径，不能替代缺陷逃逸率、权限误用率、回滚率或成本数据。

**启示**：对会修改软件或观察生产环境的 Agent，“已完成”应至少拆为：变更已产生、隔离测试已通过、外部依赖模拟已覆盖、生产观测无异常、人工/策略批准已满足。每层应保存输入版本、可用权限、实际命令/工具、测试夹具、输出证据、未覆盖项和回滚位置；模型的自然语言总结不能作为唯一验收物。

**建议动作**：先在非生产环境设计一条端到端验证合同：为每个连接器规定可模拟的响应、真实调用白名单、失败注入、覆盖范围、阻断阈值和升级人。要求 Agent 输出可复跑测试、运行记录和明确未测试项；只有在变更可回滚、观测可关联、人工接管可用时，才逐步增加它可触及的系统范围。

## Agent 开发平台

本窗口没有发现火山引擎 AgentKit/VeADK、Google ADK/Agent Platform、Microsoft Agent Framework/Foundry 或 AWS AgentCore 可精确归属到过去 24—48 小时的新 GA、Preview 状态变化或 API 破坏性变更。AWS AgentCore Release Notes 的九月分组仍可见 TypeScript 评测支持和 Consent Portal，但单个条目没有可用的精确发布时间；它们不因被今日再次抓取而重复记为新增。9 月 17 日前的 AWS Agent Registry namespace 迁移风险亦已在上一期记录，本期继续作为迁移检查项而非新功能发布。[AWS Release Notes](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/release-notes.html) · [Registry 迁移提示](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/registry-prerequisites.html)

平台侧应优先验证“路由后谁负责”的边界：模型选择服务可以选择推理引擎，但不能代替应用决定工具授权、身份委托、审批、幂等、审计与业务验收。若任务在模型切换后出现不同的工具调用或输出结构，控制面应能够定位是策略变更、模型行为、工具适配还是下游系统问题。

## 数字员工 / AI Worker

Claude Cowork、豆包工作、Qoder、Kimi Work、Manus 与 Genspark 在本窗口没有确认到可进入日报的官方开放范围扩大或企业上线事实。Perplexity 案例可作为 Worker 设计的一个实践信号：可信度不应由“少查看几次”来定义，而应由运行前权限、运行中的可观察状态、运行后可复核证据和异常时人工接管共同决定。

对于消息、客户记录、文件或生产系统等带副作用的场景，应把任务状态分成 `计划`、`等待授权`、`执行`、`验证`、`需人工确认`、`已闭环/已回滚`。路由档位、实际模型和预算只是执行上下文的一部分，不能盖过任务拥有者与外部动作结果。

## DataAgent

本窗口未发现 Databricks、Snowflake、Microsoft Fabric、Google Conversational Analytics、ThoughtSpot 或 Tableau 的新增高价值 P0 产品事实。自动选模同样会影响 DataAgent：较低成本路由若改变结构化输出稳定性、SQL/工具调用行为或引用覆盖，表面上的 token 节省可能转化为更高的复核成本。

建议把每次数据任务的模型/路由策略同数据权限、语义层版本、查询文本/执行计划、字段裁剪、引用集、结果校验和人工发布决定关联起来。缺少任一层时，都不应将回答视作可直接采取业务行动的结论。

## 通用工作 Agent / Agentic Coding

GitHub 的更新让“Auto”从隐式默认变为可设置的优化偏好，但其仍处于分入口滚动，且不是固定模型承诺。对 Coding Agent 而言，质量档位不能自动解除分支保护、Shell/网络限制、密钥访问或 PR 审查；不同档位应该在相同的工具沙箱和同一份验证集上验证，以避免把安全配置差异误归因于模型。

OpenAI 的 Perplexity 案例补充了一个值得产品化的证据形态：外部依赖模拟 + 端到端测试 + 未覆盖范围。相比“模型说已修复”，可回放的测试程序和运行结果更能支撑代码审查；但测试模拟本身也可能遗漏真实限流、权限、时序、数据质量与故障恢复，必须保留 production-like 验证和回滚门槛。

## 基础模型与 Agent Infra

本期没有新的基础模型正式发布。GPT-6 Astra 的 API 上下文窗口、工具支持、定价及安全边界已在此前日报确认，不重复计分。当前官方模型页仍显示其有 1,050,000 token 上下文、128,000 token 最大输出，Responses API 工具列表包含 web/file search、hosted shell、computer use、MCP 与 tool search；这些能力说明可组合的工具面较广，但不说明任何账户或业务场景已获相同权限。[OpenAI GPT-6 Astra 模型页](https://developers.openai.com/api/docs/models/gpt-6-astra)

这也给路由设计一个约束：只要不同模型/快照的工具、结构化输出、推理预算或安全行为不完全相同，自动选模就必须有 capability gate。应用应先检查任务所需的工具/地区/数据处理与安全要求，再在合格池内按成本和质量路由；不能先选到便宜模型，再临时降低任务合同。

## AI 与模型平台 / AI 基础

自动模型选择会把模型平台的复杂性前置到产品与财务治理：每次执行的成本取决于实际选中模型而不是用户选择的偏好名称。企业需要按任务类型、入口、档位和真实模型聚合成本，并把异常成本与重试、人工介入、拒绝的工具调用一并观察。只有同时看到质量和副作用，才能避免把更低的单次推理账单误解为更低的单位交付成本。

## 风险与反信号

- Copilot 的三档偏好正在滚动，且使用同一可用模型池；档位并非确定模型、确定账单、确定性能或跨入口同步开放的承诺。
- Auto 按实际选中模型计费。若缺少任务级实际模型和成本记录，财务团队难以复盘异常消耗，产品团队也无法定位质量漂移。
- Perplexity 案例是客户与供应商一手叙述，未披露独立评测或生产事故数据；“更少查看”不应被转译为无需审核。
- 测试程序模拟 connector/API 可提高端到端覆盖，但模拟不等于真实凭证、限流、时序、数据质量和故障恢复已被验证。
- GitHub Trending 和主题搜索中的活跃度是发现线索；没有 P0 Release/文档/维护者公告支撑时，不应把其当作能力成熟或企业采用。

## 今日建议深挖

建立一份“路由—任务证据卡”，用于所有会自动选模、调用工具或产生外部副作用的任务。最小字段包括：`任务目的与风险级别、策略档位、候选模型池与实际模型/快照、上下文/缓存配置、工具及权限、成本与时延、测试或引用证据、质量阈值、人工介入、外部副作用、回滚位置和最终验收`。

**验收标准**：对同一批代表任务，能够回答“这次实际用了什么模型、为什么允许它调用此工具、结果如何验证、成本与返工是否变化、发生异常时谁能停止或回滚”。若无法回答任一问题，就不应把自动路由扩大到高风险任务。
