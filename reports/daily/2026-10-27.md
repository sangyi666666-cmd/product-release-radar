# 企业级 Agent / AI Worker / DataAgent 行业雷达

日期：2026-10-27  
类型：延迟补跑增量日报  
观察窗口：2026-10-21 10:55 至 2026-10-27 10:41（北京时间；以来源标示的发布日期和状态为准）

## 今日结论

本窗口新增事实聚成一条比“模型又多一个”更重要的线：企业 Agent 的生产闭环开始同时要求 **可信语义、可执行的默认策略，以及可归因的实际使用记录**。Google 将 LookML 中的指标、连接和血缘语义以 GA 方式接入 Knowledge Catalog，使 Gemini Enterprise 与自建 Agent 可以在受治理的上下文内取得确定性指标定义；GitHub 则连续补齐 Copilot 的全局默认策略、客户自定义能力名称和多客户端模型用量记录。三者都不是“准确性/治理已经自动解决”的承诺，却把原来难以审计的环节变成可配置、可观测或可回归的对象。

模型层的新增是 GPT-6.1 Terra 在 GitHub Copilot 的 GA。它已列入多个 Copilot 入口和付费计划，但仍是逐步推出，企业管理员也可通过 model policy 管控；因此“已 GA”“租户允许”“用户看见”“某次任务实际选中”依旧是不同状态。Google 对内部 Project Fortify 的公开说明则提供了反面约束：即使漏洞发现、分诊与补丁生成可由 Agent 串联，最终合并和安全发布仍保留在人类工程与 SRE 的控制下。

本期没有确认新的基础模型原厂正式发布。已复查 OpenAI GPT/Codex、Anthropic Claude、Google Gemini、DeepSeek、通义、豆包、混元、Kimi、GLM 的公开入口；GPT-6 Astra 的正式发布、API/产品入口、工具、上下文、定价和安全边界已有记录，本期不重复计分。

## Top Signal

### 1. LookML 语义索引进入 Knowledge Catalog GA：DataAgent 可把“指标怎么算”从提示词迁入受治理上下文｜88 分

**可验证事实**：Google Cloud 于 10 月 26 日宣布 Looker Core on Google Cloud 的 LookML 语义语言索引已在 Knowledge Catalog **GA**。官方说明会将已解析的 LookML models、Explores、Views、字段、连接关系、血缘和仪表板索引到目录；Gemini Enterprise 与自建 Agent 可通过 Knowledge Catalog/LookupContext API 取得该上下文。对于已启用相关能力的 Gemini Enterprise 联邦查询，官方称 Agent 以终端用户身份访问其有 IAM 权限的数据资产，并可取得 LookML 的指标公式和 join 定义。[Google Cloud 公告](https://cloud.google.com/blog/products/business-intelligence/lookml-metadata-indexing-in-knowledge-catalog-is-now-ga/)

**产品判断**：这是 DataAgent 从“读取表描述后猜 SQL”向“检索已建模业务语义后生成 SQL”的重要基础设施变化。它不代表每个 LookML 模型正确、每个自然语言问题可无歧义解析，亦不等于连接器权限、数据新鲜度或最终业务结论已被验证。

**启示**：可信 DataAgent 的语义合同至少应可追溯到指标定义、有效过滤条件、粒度、join 路径、数据质量/PII 标签和血缘，而不是只保存一次生成 SQL。语义层与数据目录是不同责任：目录回答“有什么与谁能看”，语义层回答“这个数按什么规则算”。

**建议动作**：选取收入、退款或跨粒度连接等最容易产生 fan-out 的真实问题，比较裸表 NL2SQL 与经语义层检索后的输出；逐题回放公式、过滤器、join、权限拒绝、引用和人工复核。将“可复现指标正确率”和“权限/血缘解释完整率”设为验收指标，而不只看回答流畅度。

### 2. GPT-6.1 Terra 在 GitHub Copilot GA，但租户实际可用仍取决于分批推出与模型策略｜84 分

**可验证事实**：GitHub 于 10 月 26 日宣布 GPT-6.1 Terra 在 GitHub Copilot **GA**，定位为较 GPT-6.1 Sol 成本更低的日常 agentic coding 与终端任务模型，并按 provider list pricing 进行 usage-based billing。公告列出 VS Code、Visual Studio、Copilot CLI、cloud agent、Copilot app、github.com、移动端、JetBrains、Xcode 与 Eclipse 等入口；适用 Pro、Pro+、Max、Business、Enterprise，但明确为逐步推出。Business/Enterprise 管理员可借助 model policy 管控访问，新模型在未关闭全局默认或未被显式禁用时默认启用。[GitHub Changelog](https://github.blog/changelog/2026-10-26-gpt-6-1-terra-in-github-copilot/)

**产品判断**：这是一项产品入口与模型生命周期变化，而非 OpenAI API 的普遍可用性声明。厂商对早期测试的终端/C# 表述不是组织任务、费用、工具调用或安全表现的 SLA；逐步推出也意味着计划、地区、客户端和管理员策略都可能造成同日差异。

**启示**：模型目录更新应进入变更管理：供应商状态、套餐/地区资格、企业 policy、客户端可见性、实际 model ID、token/费用和基准结果必须关联。仅截图或控制台开关无法证明任务实际运行在目标模型上。

**建议动作**：为既有 Coding Agent 的低风险任务建立 Terra 与现有默认模型的并行黄金集；固定 repo、工具权限、预算和超时，记录任务成功、测试/安全扫描、人工接受、P50/P95、模型路由与总成本。待回归达标后再调整默认策略或自动 PR 范围。

### 3. Copilot 用量 API 补齐“哪个客户端、哪个模型、怎样选中”的服务端观测｜83 分

**可验证事实**：GitHub 于 10 月 23 日为 Copilot usage metrics API 增加 `totals_by_client`。企业、组织及其用户的 1 日/28 日报告可按客户端返回成功模型请求数、会话数、输入/输出 token 与每请求平均 token，并可按模型和 `user_selected`、`auto`、`product_selected` 等选择方式细分。官方列举 `opencode`、`claude_code`、`codex`、`zed`、`copilot_cli`、`github_app`、`cloud_agent`、`code_review`、VS Code 与 JetBrains 等客户端；它也明确该字段是集成 ID 的尽力分组，request count 是模型调用而非 prompt 数，部分旧/未标准化值会归入 `other` 或 `unknown`。[GitHub Changelog](https://github.blog/changelog/2026-10-23-usage-metrics-api-adds-usage-from-tools-like-opencode/)

**产品判断**：这把多入口 Coding Agent 的消耗和模型路由纳入同一服务端观测面，有助于预算、支持与治理；它不构成用户身份、业务价值、任务成功率或精确成本归因的充分证据。

**启示**：企业不能只按 IDE 统计 Agent 使用。至少应把客户端、任务/会话、请求、解析模型、选择模式、token、工具权限、代码产物和人工验收分开建模；否则无法判断成本变化来自模型、入口、自动路由还是任务结构。

**建议动作**：在启用前核对 metrics policy 与读取权限；建立每日聚合与异常阈值，并用一批已知任务把 usage 报告同 CI、PR、Agent job 和费用账单做抽样对账。不要把 `request_count` 直接当成用户提问数或生产力指标。

### 4. Copilot 对自定义 Skill、Agent 与 MCP Server 开放命名用量，扩容不等于精确计费｜81 分

**可验证事实**：GitHub 于 10 月 22 日更新 Copilot usage metrics：企业与组织报告中的 `totals_by_skill`、`totals_by_custom_agent`、`totals_by_mcp`、`totals_by_slash_cmd`、`totals_by_plugin` 将展示已配置的客户自定义名称，单个列表由最多 5 条提升至最多 25 条，其余聚合为 `other`。适用范围包含 Copilot CLI、Copilot app、Copilot SDK 客户端及 ACP integrations；部分入口要求 CLI 1.0.97+ 或 SDK 1.0.21+，非 SDK 的 IDE integrations 不会报告名称。GitHub 还提示该类指标来自客户端 telemetry，可能因客户端过旧或 telemetry 被阻断而低估，且历史日期不会回填名称。[GitHub Changelog](https://github.blog/changelog/2026-10-22-custom-skills-agents-and-mcp-servers-in-usage-metrics-api/)

**产品判断**：这是自建能力采用度的可见性改进，不是对 MCP/Skill 安全性、实际工具执行、业务效果或按名称的精确结算承诺。名称自身也可能泄露内部项目线索，官方要求在共享报告前审查名称。

**启示**：给自定义 Skill、Agent、MCP Server 命名时应同时设定受控命名规范、版本、owner、权限域和退役日期；采用度指标只作为运营信号，应与调用审计、失败/拒绝、人工接管和业务结果结合。

**建议动作**：先清点会进入报表的名称，移除内部敏感表述；对 top 使用项建立“用途—owner—权限—版本—审批—实际调用证据”清单。对低采用但高权限能力优先做风险检查，不能因用量低而默认安全。

### 5. Copilot 全局默认策略开始生效：未配置的 GA 功能会一次性落到组织的默认选择｜80 分

**可验证事实**：GitHub 于 10 月 22 日宣布 Copilot Business/Enterprise 的 global default policy 开始分批执行，发布说明称 rollout 持续至 10 月 26 日，企业和组织生效时间可能不同。对符合条件且仍为 Unconfigured 的 GA features/capabilities，策略会按选定的 Enabled、Disabled 或 Let organizations decide 一次性落地；之后改动全局默认值不会再改写已被设置的 feature policy。已显式配置的设置会保留，Preview 保持 opt-in；覆盖范围包括 Features & clients 与 MCP servers in Copilot 的合格设置。[GitHub Changelog](https://github.blog/changelog/2026-10-22-global-default-for-copilot-features-generally-available/)

**产品判断**：这是默认授权面从人工逐项设置转向策略化控制的变化，适合降低漏配，但不能替代功能级风险评审。一次性落地与企业间分批生效意味着“今天改了总开关”不必然同步改变每个功能的既有实际状态。

**启示**：企业需要在策略生效前后保存 policy 快照，并把“不配置”的含义从模糊状态变成可审计选择。对 MCP、云端 Agent、自动代码操作和新模型等高副作用能力，应明确谁能覆盖默认、例外何时失效以及如何回滚。

**建议动作**：拉取并复核 Features & clients、MCP servers 与各层 model policies；标出仍为 Unconfigured 的生产范围，按风险分级转为显式选择。使用真实客户端与受控任务验证策略解析，不只依赖管理控制台显示。

## Agent 开发平台

本窗口未确认 AWS Bedrock AgentCore、Microsoft Agent Framework/Foundry、Google ADK/Agent Platform、火山 AgentKit/VeADK 的新 GA 或普遍可用范围变化。Copilot 的三项治理/可观测性更新可作为任何 Agent 平台的控制面核对表：默认策略必须可导出、实际使用必须带客户端与模型维度、自定义能力必须可被安全地归属与退役。

## 数字员工 / AI Worker

未确认豆包工作、Qoder、Claude Cowork、Kimi Work、Manus、Genspark 等的新增 P0 普遍可用事实。对岗位型 Worker 而言，本文关于“命名指标”和“默认策略”的教训更直接：一个能看到使用量的自定义 Agent 不等于其已获业务授权、完成审批或产生合格结果；最终仍要按读取、判断、建议、审批、回写、通知与异常升级逐段验收。

## DataAgent

LookML 与 Knowledge Catalog 的 GA 使语义定义、血缘与治理上下文可以被企业 Agent 统一检索，是本期最具可迁移价值的 DataAgent 信号。它尤其针对指标漂移和一对多 join 放大两类常见错误；但数据质量、模型行为、权限配置和业务口径本身不会因索引而自动正确。优先把高风险指标做成可版本化的语义资产，再让 Agent 读取，而不是在每轮对话中重新推断口径。

## 通用工作 Agent / Agentic Coding

GPT-6.1 Terra 的 GA 与 GitHub 用量 API 的连续更新共同改变了 Coding Agent 的运营条件：模型选择可以更细，模型调用也能按客户端和选中模式查看。仍应坚持四段核验——供应商提供、组织允许、客户端可见、任务实际解析与验收——并将每次 model policy 变更与基准回归绑定。

## 企业案例

Google 于 10 月 26 日公开其内部 Project Fortify 的 find-fix-deploy 架构：Gemini 驱动的扫描 harness 发现问题，分诊 Agent 结合实际运行环境过滤噪声，CodeMender 类方案在 sandbox 中生成和验证修复，再由人类工程师 review/merge，SRE 通过 canary 推送。[Google Cloud 案例](https://cloud.google.com/transform/how-google-does-it-using-agents-help-find-track-and-fix-vulnerabilities) 这是企业实践披露，不是可采购产品或普遍效果证明。它的有效边界恰在于保留高精度门槛、人审合并和分阶段部署；不要把“自动生成补丁”误读为可取消安全责任。

## AI 与模型平台 / AI 基础

本期组合出的最小运营闭环是：

- **语义与数据层**：指标、join、血缘和 IAM 约束有可检索、可版本化的来源；
- **策略层**：GA 功能和 MCP 等能力的默认、例外和生效范围能导出并审查；
- **执行观测层**：客户端、模型、选择方式、token 与会话有服务端记录；
- **交付层**：代码、数据或业务动作仍由测试、引用、审批、人工接受与回滚闭环。

任何一层缺失，所谓“Agent 已上线”都可能只是页面可见或调用发生，而不是受控的业务交付。

## 风险与反信号

1. Terra 在 Copilot 的发布为逐步推出；GA 不能写成每个用户立即可选。
2. Copilot usage metrics 的客户端识别、telemetry 与 request count 都有明确局限，不能直接推导用户人数、prompt 数、精确成本或产出价值。
3. 全局默认策略只一次性处理符合条件且未配置的 GA 功能；Preview 仍需 opt-in，已显式设置不会被总策略追溯改写。
4. LookML 索引减少 Agent 重猜业务语义，但错误的 LookML、权限映射、数据延迟和不完整血缘仍会产生错误结论。
5. Project Fortify 是 Google 的内部实践披露；不可把其流程、效果或组件可用性外推为外部客户已取得相同结果。
6. GitHub 发现扫描只用于线索：226 个去重候选不代表项目质量、成熟度或企业可用性。

## 今日建议深挖

1. **DataAgent 语义验收**：针对三个高风险指标建立“自然语言问题—语义定义—SQL—结果—血缘—权限”回放链路，先验证错算与 fan-out 是否下降。
2. **Coding Agent 模型变更 runbook**：把供应商发布、管理员 policy、客户端可见性、实际 model ID、费用和黄金集回归连成一次可回滚变更。
3. **自定义能力治理**：为 Skill/Agent/MCP Server 建立命名、owner、权限、版本、遥测、停用与人工接管清单，并审查会外发的 metrics 名称。
