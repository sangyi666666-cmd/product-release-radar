# 腾讯云 WorkBuddy 开放平台产品发布调研

> 发布事件：WorkBuddy 开放平台正式上线  
> 调研日期：2026-09-02  
> 补充更新：2026-09-04（Agent 开发、Runtime、生命周期管理与硬件生态）  
> 研究状态：发布当日快研，基于公开资料，未完成第三方资产上架实测  
> 结论置信度：高（产品结构）；中（生态规模与商业效果）

## 决策摘要

1. **是什么：**面向开发者、ISV、企业技术团队和硬件伙伴的 Agent 生态平台——把 WorkBuddy 的多 Agent 运行底座、桌面/云端执行、用户入口与资产市场开放给第三方。本体服务最终用户；开放平台负责「第三方能力如何进来、如何触达用户」。
2. **不是什么：**现阶段不宜叫「通用 Agent OS」。更准确的定位是：**桌面办公 Agent 的运行时 + 能力市场 + 分发平台**。要成 OS，还缺成熟工具链、资产治理、版本兼容、商业结算与跨宿主标准。
3. **现在能做什么：**供给路径已从轻到重打通（Skill → 专家/专家团 → 连接器 → 企业自建 Agent → Buddy 应用）；OAuth / Open API / ACP / MCP / CLI 与本地助理、云端任务可用；企业侧初具创建—Test Run—发布—Runtime/Session—评测的 AgentOps 骨架。
4. **还缺什么：**开发者收费与分成、流量规则、API 配额/计费、SLA、恶意资产治理、灰度回滚等未公开；首页「10 万+资产 / 3000 万+安装」属厂商口径。远程驱动本地助理的安全与审计，是当前最大红线。
5. **建议动作：**低风险试点用 Skill、专家或只读 MCP；涉及本地助理远程执行或敏感写操作，先等权限/审计补齐，或自建二次确认。关键胜负手看未来 3–6 个月的活跃开发者、审核时效、留存、任务成功率与第三方收入——不是首发资产数量。

## 1. 执行摘要

2026-09-02 上线的是「开放平台」，不是 WorkBuddy 本体首次发布。WorkBuddy 是面向最终用户的全场景 AI 办公工作台；开放平台把外部行业知识、SaaS、工具、应用和硬件，变成可在 WorkBuddy 中运行与分发的能力资产。

核心链路：

```text
第三方行业知识 / 数据 / API / 软件 / 设备
                ↓
Buddy 应用 / 专家与专家团 / Skill / 连接器 / 第三方应用 / 硬件
                ↓
WorkBuddy Agent 底座
多 Agent + 上下文压缩 + 记忆 + 工具编排 + 沙箱 + 权限
                ↓
桌面本地助理 / 云端长任务 / 移动与 IM / 行业应用 / 智能硬件
                ↓
个人用户与企业客户
```

相对一般 Agent Builder，辨识度最高的组合是：**桌面本地执行 + 云端长任务 + MCP/CLI 连接器 + OAuth/Open API + 行业应用 + 硬件入口**。开放的不只是模型调用，还包括向 PC 本地助理下发任务、创建云端任务、ACP 实时通信和拉取任务产物。

发布当日已有入驻、实名、资产规范、OAuth、Open API、审核与发布文档。官方称首批共创伙伴 100+、联名硬件 9 款、行业应用 30+（覆盖 20+ 领域）；平台首页另有「10 万+生态资产、3000 万+累计安装」——**无公开统计方法，按厂商口径记录，不作独立活跃生态证据**。

短板不在能力清单，而在平台运营与企业治理：开发者收费/分成、流量分配、API 配额与计费、SLA、数据地域、恶意资产检测、灰度与回滚等规则尚未公开。技术骨架已立，商业闭环与规模运营仍待 3–6 个月验证。

与内部常见参照的粗对照（便于对齐认知，非完整竞品章）：

| 参照 | 相似点 | 差异（WorkBuddy 开放平台侧） |
| --- | --- | --- |
| JoyAgent 类底座开放 | 提供 Agent 底座，减少重复造外壳 | 更强调桌面本地执行、IM 遥控与硬件触点 |
| HRDataAgent / 小财神类行业工作台 | 可做成垂直岗位/场景工作台 | 此处是「平台壳 + 伙伴装行业 Know-how」，不是单一垂直产品本身 |

产品边界一句话：**开放平台是生态前门；WMA（Managed Agents）是生产运行与管理后场**；当前公开材料未证明开放平台开发者可直接使用 WMA 全套 Runtime 与管理台，故下文分述。

### “五类能力”为什么看起来不一致

平台首页把首期能力列为 **Buddy 应用、专家、Skill、连接器、硬件**；发布报道则把技能、专家、专家团、连接器、外部应用并列。公开文档实际还覆盖第三方应用与 Open API。

更合理的理解是：专家团属于专家类资产；Buddy 应用和第三方应用承载完整场景；硬件使用第三方应用与 Open API 体系接入。因此本报告不机械限定为唯一“五项”，而按完整生态对象分析。

## 3. WorkBuddy 本体与开放平台的关系

### WorkBuddy 本体：最终用户的执行工作台

官方将 WorkBuddy 定位为全场景 AI 办公工作台。用户用自然语言下达任务，系统自主拆解和调用工具，可处理文档、表格、代码、图片等内容，在授权目录读写本地文件，并交付可直接验收的文件结果。它还提供领域专家、云端助理和多 Agent 项目空间。

本体解决的是“用户如何让 Agent 干活”；开放平台解决的是“第三方如何把自己的能力放进 WorkBuddy，并触达 WorkBuddy 用户”。

### 开放平台：四层角色

1. **供给层**：开发、上传和维护 Skill、专家、专家团、连接器与 Buddy 应用。
2. **运行层**：复用 WorkBuddy 的多 Agent、记忆、上下文、工具编排、文件处理、沙箱与权限能力。
3. **接入层**：通过 OAuth 2.1、REST Open API、ACP 实时通道、MCP 或 CLI 连接第三方系统。
4. **分发层**：把能力放入专家、技能、连接器和行业应用市场，并延伸到外部应用及硬件。

腾讯提出把 WorkBuddy 做成“Agent 时代的操作系统”。从现阶段证据看，更准确的定位是**桌面办公 Agent 的运行时、能力市场与分发平台组合**。要成为通用 Agent OS，还需要成熟的开发工具链、资产治理、版本兼容、商业结算与跨宿主标准。

### 开放平台、WorkBuddy 与 WMA 的能力边界

| 层级                            | 主要职责                                                     | 主要用户                   |
| ----------------------------- | -------------------------------------------------------- | ---------------------- |
| WorkBuddy 开放平台                | 生态主体入驻；Skill、专家、连接器、Buddy 应用和硬件接入；OAuth/Open API；审核与市场分发 | 开发者、ISV、行业和硬件伙伴        |
| WorkBuddy 本体                  | 承接用户任务；使用专家和 Skill；读写本地文件；调用工具；运行桌面或云端任务                 | 个人与企业办公用户              |
| WorkBuddy Managed Agents（WMA） | 托管企业自建 Agent，提供生产级 Runtime、独立沙箱、Session、Trace、评测和生命周期治理  | 企业 IT、平台工程和 Agent 开发团队 |
| WorkBuddy Enterprise          | 统一承载 WorkBuddy、CodeBuddy 与 WMA 的企业账号、购买、治理和交付体系          | 企业管理员与采购方              |

**分析判断：**开放平台更像生态“前门”，WMA 更像生产运行与管理“后场”。二者共享 WorkBuddy Harness 方向，但当前公开材料没有证明开放平台开发者能够直接使用 WMA 的全部 Runtime 与管理控制台，因此报告对两者分别表述。

### 从 Agent 技术平台视角看四条主线

#### Agent 开发：从能力包到完整行业工作台

平台提供了一条逐级加深的开发路径：

```text
Skill：把知识、SOP、脚本和模板做成最小复用单元
  ↓
专家：给能力增加角色、人设、方法论和工具依赖
  ↓
专家团：加入主理人、多个成员 Agent 和协作流程
  ↓
连接器：通过 MCP 或 CLI 接入外部数据与执行工具
  ↓
企业自建 Agent：配置模型、Prompt、规则、Skill、插件、MCP、子 Agent 和工作空间
  ↓
Buddy 应用：组合以上能力，形成带品牌、场景、模型和市场的行业工作台
```

企业自建 Agent 使用声明式 Manifest 描述身份、能力、工作空间和运行环境，可配置代码仓库、初始化命令、环境变量和 Secret，并用 Test Run 在发布前验证。凭据由代理层在运行时解密注入，不必写进配置或沙箱文件。

这条路径兼顾非技术行业专家和专业开发团队：前者可从 Skill/专家开始，后者可使用 MCP、子 Agent、Manifest、API 与云端沙箱。当前短板是开发体验仍分散在开放平台配置、压缩包资产和企业后台之间，尚未看到统一 SDK、CLI、调试器和本地到云端的完整 DevOps 流程。

#### Agent Runtime：为长任务准备的状态化执行环境

WMA 把 Runtime 定义为 Session 背后的独立 Agent 运行环境，每个 Runtime 包含云端 Linux 文件系统与终端、Agent Manifest，以及一个或多个 Session。与无状态模型 API 相比，它面向的是会持续几十分钟甚至长期运行、需要文件、工具和恢复能力的任务。

官方披露的关键能力包括：

* WorkBuddy Harness 内置 Agent 编排、记忆、行动和管控四层。

* 独立沙箱、数据持久化、跨节点恢复、秒级 CoW Fork、端口转发和预热池。

* 向下连接腾讯云基础设施与弹性算力，面向规模化并发。

* Agent 可在云端 7×24 小时运行；空闲 Session 会自动休眠，再次访问时唤醒。

* 每个用户通过分享链接或 API 使用 Agent 时可获得独立 Session，隔离对话历史与产出文件。

其产品价值是让企业不用自己拼装 Agent 编排、容器、状态存储、恢复和弹性系统。需要继续验证的是实际冷启动时间、长任务成功率、跨节点恢复一致性、并发配额、成本模型、SLA 和故障补偿。

#### Agent 管理：从“创建助手”走向 AgentOps

企业后台目前已披露以下管理闭环：

* **Agent 管理：**创建、编辑、克隆、删除、接入、发布和版本历史。

* **Runtime 管理：**查看创建中、运行、休眠、停止和失败状态，并定位沙箱或资源未回收问题。

* **Session 管理：**查看 Agent、Runtime、创建者、独立历史和文件状态。

* **渠道管理：**将 Session 绑定企微 AIBot、QQ 机器人、飞书或钉钉。

* **凭据管理：**加密存储，并在调用 MCP、Skill 或外部 API 时代理注入。

* **质量管理：**用评测数据集逐条运行测试并计算得分；官方产品定位还包括全链路 Trace 与持续优化。

* **企业治理：**统一身份、角色权限、数据隔离、传输/存储加密和操作审计。

这说明腾讯的目标不是只做 Agent Builder，而是构建“开发—测试—发布—运行—观测—评测—优化”的 AgentOps 平台。目前最明显的缺口仍是公开的告警、成本预算、版本灰度、回滚、审计导出、评测指标体系和 SLA 细节。

#### 硬件生态：把设备变成 Agent 的感知和触发端

WorkBuddy 正在拓展硬件生态：目标不只是把聊天框搬到设备上，而是把设备做成 Agent 的感知与触发端；目前仍处「能力接入」早期。发布材料显示，平台围绕“听、看、记、聊、协”五类触点，已覆盖智能眼镜、录音卡、麦克风、耳机、桌面陪伴设备、键鼠、PC/平板、智能穿戴和手机等十余类设备，合作品牌超过 30 家；首批 9 款联名硬件来自 Plaud、Rokid、影石、优篮子、科大讯飞、安克、猛玛和京东京造等 8 家厂商。

其集成思路不是把完整大模型塞进每个设备，而是做“端侧感知与交互 + WorkBuddy Agent 执行”：

```text
硬件：麦克风 / 摄像头 / 按键 / 屏幕
  ↓ 采集、唤醒、确认
OAuth + Open API
  ↓
WorkBuddy：身份、记忆、任务规划、工具调用、本地或云端执行
  ↓
任务状态、决策提醒、报告、纪要、邮件等产物
  ↓
眼镜 / 手机 / PC / Web 跨端查看与继续处理
```

| 硬件形态       | 设备承担的角色         | WorkBuddy 提供的增量价值         |
| ---------- | --------------- | ------------------------- |
| AI 眼镜      | 摄像、录音、语音唤醒与轻量显示 | 视觉检索、情境理解、任务规划和跨端继续处理     |
| 录音卡、麦克风、耳机 | 采集会议与现场语音       | 转写、总结、记忆检索、纪要和邮件等可交付产物    |
| 键盘麦等桌面外设   | 快捷唤醒、发送和结束任务    | 将 Agent 操作变成办公快捷入口，减少切换应用 |
| 桌面陪伴设备     | 展示状态、提醒和关键确认    | 让长任务进度和人在回路的确认从 PC 界面外显   |

这一生态对腾讯有三层价值：增加比桌面输入框更高频的任务入口；把用户账号、记忆和产物沉淀到 WorkBuddy；让硬件厂商无需独立建设完整 Agent 栈即可获得差异化能力。对硬件伙伴的风险则是对 WorkBuddy 账号、云端可用性、Credits 和接口策略形成依赖。

现阶段应把它定义为“硬件接入生态”，而不是成熟“硬件操作系统”。公开能力主要集中在应用注册、OAuth、创建云端任务、调用本地助理和获取产物；设备身份、设备群运营、固件升级、弱网/离线、实时音视频链路、端侧模型、安全芯片与设备认证尚未形成完整公开体系。首批设备中也存在 Demo 阶段产品，因此需要继续跟踪实际出货、激活、留存和跨端任务完成率。

## 4. 目标开发者与核心场景

### 目标供给者

* 将专业方法论产品化的行业专家、咨询顾问和内容创作者。

* 拥有 API、数据或 SaaS 的 ISV 与软件公司。

* 希望建设内部 Agent 能力的企业 IT、数字化与 AI 团队。

* 提供知识库、搜索、数据分析和工具服务的技术开发者。

* 智能眼镜、录音设备、耳机、麦克风等硬件厂商。

* 腾讯云、微信、企业微信和腾讯办公生态合作伙伴。

### 典型场景

* 把 SOP、模板和脚本封装成 Skill。

* 把角色、方法论、Skill 和工具链封装成专家或专家团。

* 用 MCP/CLI 把企业 API、SaaS 和数据服务接成连接器。

* 将完整垂直体验封装为带品牌、模型和市场的 Buddy 应用。

* 从外部 App 或硬件为用户创建 WorkBuddy 云端任务。

* 在用户显式授权后，向其 PC 端本地助理下达任务并查询消息。

* 获取任务计划、执行状态、媒体文件和最终总结等产物。

* 通过兑换码给用户发放 WorkBuddy Credits。

## 5. 开放能力拆解

### 5.1 Skill：最轻量的任务能力包

Skill 以 `SKILL.md` 为核心，可附带领域参考资料、脚本、模板和工具白名单。它用于告诉 Agent 在特定场景下如何工作，用户可从技能市场安装并在对话中调用。

这一形态适合可复用但不必拥有独立品牌和交互外壳的 SOP，例如报告框架、批处理步骤、特定 API 使用方法。它的优势是迁移成本低，风险则是 Skill 内脚本和依赖可能引入供应链问题，平台的扫描与签名机制尚未公开。

### 5.2 专家与专家团：把能力包装成“角色”

专家是“角色 + 方法论 + 工具链”，可以绑定 Skill、MCP 和连接器依赖。用户召唤前，WorkBuddy 会引导完成必要连接。专家团进一步组合主理人、多个成员 Agent、协作流程和共享技能，适合研究、分析或项目执行等多角色任务。

角色化包装降低了非技术用户选择能力的门槛，但平台需要持续解决专家之间能力重叠、质量评价、错误责任和更新兼容问题。

### 5.3 连接器：MCP 与 CLI 双通道

官方推荐 **MCP + Skill**：远程服务使用 HTTPS，支持 SSE 或 Streamable HTTP，本地进程可使用 stdio；另支持 **CLI + Skill**，由 WorkBuddy 安装和调度成熟 CLI，CLI 自行维护认证状态。

关键规则包括：

* 一个连接器当前配置一个 MCP Server。

* 远程地址必须使用 HTTPS，并遵循最小权限原则。

* 禁止在配置、Skill、包或示例中硬编码真实密钥。

* 敏感凭据不得出现在日志和错误信息中。

* 官方建议单次工具调用在 30 秒内响应。

* CLI 至少支持 macOS 与 Linux，建议同时支持 Windows。

* 资产打包提交并通过审核后才能进入连接器市场。

MCP 降低了既有生态迁入成本；CLI 则让传统开发工具直接获得 Agent 调度能力。两者同时开放，扩大了供给范围，也显著提高了安全审核复杂度。

### 5.4 Buddy 应用：垂直行业 Harness

Buddy 应用不是单个 Agent，而是可配置的行业工作台。伙伴可以设置：

* 行业 System Prompt 和工作模式。

* 首页引导与场景胶囊。

* 专家、专家团、Skill、连接器和精选案例。

* 可用模型、默认模型和排序。

* OAuth、可信域名及既有系统嵌入。

* 通过 MCP Apps 等方式把已有系统接入对话流。

WorkBuddy 提供多 Agent、上下文压缩、记忆、工具编排以及安全权限底座，伙伴把行业 Know-how 和现有系统“装进”这一外壳。标准流程是创建、基础审核、配置、下载本地预览、再次审核和发布；发布后更新也需要重新审核。

这一设计比从零开发独立 Agent 产品更快，但它也让合作伙伴对 WorkBuddy 的产品框架、模型池和分发机制形成依赖。

### 5.5 第三方应用、硬件与 Open API

开放平台基于 OAuth 2.1 授权码流程。当前 Open API 已覆盖：

* 获取用户资料和校验联系方式。

* 查询本地助理在线状态、发送消息和查询消息历史。

* 创建和查询云端任务。

* 获取 ACP 连接地址和短期鉴权票据，进行实时双向通信。

* 获取任务计划、任务列表、媒体和总结等会话产物。

* 核销兑换码，为授权用户发放 Credits。

值得重视的是 `user.localassistant.invokable` 类权限：第三方应用在用户授权后可驱动 PC 上的本地助理。这使 WorkBuddy 不只是一组云 API，而成为桌面执行入口；同时也让权限审批、二次确认和恶意应用防护成为平台生命线。

公开文档暂未显示用 API 批量管理 Skill、专家或连接器，这些资产目前主要通过控制台配置、压缩包上传和审核发布。

## 6. 开发者接入与发布流程

### 入驻认证

企业可以通过法人实名认证、已实名腾讯云账号或微信公众号/小程序账号完成快速认证。个人当前需要中国大陆二代居民身份证、实名手机号、邮箱和人脸识别；一个身份证只能对应一个个人主体，一个账号最多创建一个个人主体。医疗、金融、教育、新闻等行业还需按服务类目提交资质。

### 应用生命周期

```text
主体认证
→ 创建资产或应用
→ 配置能力、权限和凭据
→ 本地预览 / 自测
→ 提交平台审核
→ 发布到市场或启用 API
→ 版本更新后重新审核
```

这个流程已经具备平台治理基本形态，但官方没有公开平均审核时效、驳回申诉、灰度发布、紧急下架、版本回滚和兼容性政策。

## 7. 权限与安全

OAuth 使用授权码模式，回调地址需要和登记值一致，`state` 用于防止 CSRF，授权码一次性使用且有效期 10 分钟。应用创建后生成 `client_id` 和只完整展示一次的 `client_secret`。公开 Scope 已细分到资料、联系方式、Credits、本地助理和云端任务的可读/可调用权限。

ACP 支持服务端发出权限请求，让客户端要求用户确认工具执行或回答问题，说明平台已把“人在回路”考虑进远程 Agent 协议。但以下关键问题尚未公开：

* 哪些动作被强制归类为高风险并必须确认。

* 本地助理获得调用权限后，对具体文件夹与系统工具是否还有第二层隔离。

* OAuth Token 的主动撤销接口、开发者审计日志和终端用户授权管理。

* API 限流、滥用防护、数据存储地域和保留周期。

* 恶意 Skill、CLI、MCP Server 的静态扫描、运行隔离和供应链签名。

* 安全事件响应、版本下架、回滚和漏洞披露流程。

此外，官方文档存在 Token 有效期不一致：第三方应用页称 `access_token` 有效 24 小时，Open API 示例返回 `expires_in: 3600`，即 1 小时。接入方应以实际接口返回值为准，并等待官方澄清。

## 8. 腾讯生态协同

腾讯的差异化不只来自混元模型，而来自渠道、办公数据与云交付的组合：

* **身份与伙伴：**腾讯云企业实名、微信公众号和小程序主体可以复用认证。

* **办公上下文：**WorkBuddy 已与腾讯文档、腾讯乐享等知识和内容产品形成连接。

* **移动触达：**官方文档显示可通过微信、企业微信、QQ、飞书、钉钉等渠道远程下发任务。

* **本地执行：**桌面端读取授权文件并调用本地工具，补足传统云端 Agent 无法触达个人工作环境的问题。

* **企业交付：**WorkBuddy Enterprise 提供 SaaS、专有云和私有化选项，Managed Agents 使用 WorkBuddy Harness、独立沙箱与腾讯云弹性基础设施。

* **多模型：**Buddy 应用可从平台模型池选择混元、DeepSeek、Gemini、GLM 等模型，平台竞争不完全绑定单一模型。

战略上，微信/企微负责触达，腾讯文档等提供工作上下文，WorkBuddy 执行任务，腾讯云承接企业治理与部署。若各层身份和权限能够真正贯通，这会比单一 Agent 市场形成更强的闭环。

## 9. 定价与商业模式

WorkBuddy 最终用户的订阅已较清晰：个人体验版免费，标准/高级/旗舰版月付分别为 99、199、999 元；企业旗舰版为 198 元/人/月、1 人起购，企业专享版为 316 元/人/月、100 人起购，私有化版询价。WorkBuddy 与 CodeBuddy 共用账号和 Credits，消耗与模型、Token 和任务复杂度有关。

但以上是 WorkBuddy/Enterprise 的终端用户价格，不等于开放平台的开发者商业规则。截至调研时，未发现公开的：

* 开发者入驻费或 API 单独计费。

* Skill、专家、连接器和 Buddy 应用收费规则。

* 开发者分成、结算周期、退款和税务政策。

* 流量推荐、排名、投放和推广规则。

* 硬件授权费用或最低商业承诺。

Open API 已提供 Credits 兑换码能力，说明合作方可以为用户补贴使用额度。当前最可能的商业逻辑是：先用生态扩张场景和分发，带动 WorkBuddy 订阅与 Credits 消耗，再逐步建立伙伴分成；后半段仍属分析推断。

## 11. 优势、风险与未知项

### 主要优势

* 开放的是执行型 Agent 闭环，而不只是聊天或模型推理接口。

* Skill、专家、专家团、连接器和 Buddy 应用形成从轻到重的多层供给体系。

* 同时提供本地助理与云端任务 API，桌面执行入口稀缺。

* MCP 和 CLI 兼容既有服务与工具，降低生态迁移成本。

* 腾讯 IM、办公产品、云部署与硬件伙伴构成多触点分发。

* OAuth Scope、平台审核、沙箱和人机确认已经进入基础设计。

### 主要风险

* 远程驱动本地助理的安全责任远高于普通对话应用。

* WorkBuddy、Enterprise、Managed Agents、CodeBuddy 和 ADP 的边界复杂，容易造成产品认知和采购混乱。

* 开发者缺少公开分成和流量规则，难以计算生态投入回报。

* Token 有效期和“五类能力”口径存在不一致，反映文档仍在早期建设。

* SLA、限流、监控、灰度、回滚、安全扫描和数据政策披露不足。

* 对腾讯身份、入口和办公生态依赖，非腾讯体系客户会关注锁定风险。

* 首页生态规模为官方自报，不能替代活跃开发者、留存和付费等运营指标。

## 13. 综合判断与建议

这次发布的战略意义是，腾讯开始把 WorkBuddy 从一个“腾讯自己做能力”的桌面 Agent，升级为“第三方共同供给能力”的平台。其护城河假设不是模型绝对领先，而是同时控制用户入口、桌面上下文、云端运行、办公数据、IM 渠道和硬件触点。

对开发者而言，当前最适合低风险试点的是 Skill、专家或只读型 MCP 连接器；涉及本地助理远程执行、敏感数据写入或高风险业务动作时，应等待更清晰的权限、审计和安全机制，或自行增加二次确认与最小权限隔离。

真正决定平台能否成立的指标不是首发资产数量，而是未来 3—6 个月的活跃开发者、审核周期、安装到留存转化、任务成功率、单位任务成本、第三方收入和安全事件。若腾讯能够补齐开发者收益闭环与企业治理，WorkBuddy 有机会成为国内少数同时覆盖“桌面执行、云 Agent、IM 和硬件”的 Agent 生态入口。
