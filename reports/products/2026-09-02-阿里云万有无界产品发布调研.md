# 阿里云“万有无界”产品发布调研

> 发布事件：企业级人与多 Agent 协作平台开启公测  
> 调研日期：2026-09-02  
> 研究状态：发布当日快研，基于公开资料，尚未完成企业级实测  
> 结论置信度：中高

## 1. 执行摘要

**一句话定义：**万有无界是一个面向企业团队的“人与多 Agent 协作工作台”，用项目空间组织人、Agent、群聊、技能与文件资产，让复杂任务从提出目标、拆解分工、执行追踪走到验收和复用。

它不是典型的聊天机器人，也不是底层 Agent 开发平台。其产品判断是：企业采用 Agent 的主要障碍已从“有没有模型能力”转向“多个 Agent 如何围绕真实工作分工、谁负责推进、人在何处确认、过程和结果如何沉淀”。因此，万有无界把协作关系和任务语义做成产品主干，而不是把多个 Agent 简单放在同一个聊天窗口。

本次公测已经展现出较完整的最小闭环：

`创建项目 → 配置或接入 Agent → 一项任务建立一个群聊 → 小有澄清和拆解 → 多 Agent 接力 → 人工确认关键决策 → 结果归档到资产库 → 后续任务复用`

最值得关注的差异点有三个：第一，用“项目—群聊—任务—资产”承载长期工作；第二，允许云端 Agent 与本地 Claude Code、OpenClaw 等 Agent 进入同一协作空间；第三，以“小有”作为项目管家，明确把澄清、拆解、追踪、阻塞升级和验收收口产品化。

但它仍是公测产品。公开资料尚不足以证明组织级身份治理、审计、部署隔离、服务等级、规模化运营和第三方生态已经成熟；官方计费页面内部还存在前后口径不一致。现阶段更适合创新团队、小型项目组和愿意共同打磨流程的企业试点，不宜仅依据发布信息直接作为大规模关键业务系统采购。

## 3. 产品定位：从“回答问题”转向“推进工作”

官方对比非常明确：普通对话工具解决“问一个问题”，万有无界试图解决“推进一件事”。两者差别不只在 Agent 数量，而在工作结构：

| 维度 | 普通 AI 对话 | 万有无界 |
| --- | --- | --- |
| 工作对象 | 一段会话 | 一个持续推进的项目或任务 |
| 参与者 | 人与单个助手 | 多人、多个职责固定的 Agent |
| 协调方式 | 人不断追问和复制上下文 | 项目管家拆解、路由、追踪与收口 |
| 责任边界 | 模型角色随提示变化 | Agent 有名称、职责、技能和运行状态 |
| 结果归属 | 留在聊天记录或手动复制 | 文件自动进入会话资产、项目资产或个人知识库 |
| 能力扩展 | 模型内置能力 | Skill、MCP、第三方 Agent 与本地 Agent |

### 目标用户

- **直接用户：**运营、客服、销售、法务、研发、项目管理等需要跨角色协同的企业团队。
- **流程所有者：**项目负责人、部门负责人、AI 创新团队，希望把隐性经验和 SOP 变成可复用的 Agent 配置。
- **技术协作者：**已经使用 Claude Code、OpenClaw 或自建 Agent，希望将本地执行能力接入统一协作空间的团队。

### 优先场景

官方模板覆盖调研、内容、法务、金融等任务。最匹配的不是一步即可完成的小问答，而是具有多角色、多个中间产物、需要复核和可能反复修改的任务，例如竞品调研、营销内容生产、财报分析、视频方案、法务审阅和跨职能项目推进。

## 4. 产品对象与方案架构

万有无界由五个核心对象组成：

```text
企业 / 团队
└── 项目空间
    ├── 人员成员
    ├── Agent 成员
    │   ├── 小万：个人入口与导航
    │   ├── 小有：项目管家与协调者
    │   └── 普通 Agent：按职责执行任务
    ├── 群聊（一个群聊对应一个任务）
    │   ├── 消息与人工确认
    │   ├── Agent 接力与任务节点
    │   └── 文件输入和执行产出
    └── 项目资产

能力与资源层：Skill / MCP / 第三方 Agent / 本地 Agent / 模型 / 沙箱
治理层：项目角色 / OAuth / 资源权限 / 消耗明细 / 企业管理能力
```

### 三类关键角色

1. **小万（个人助理）**是平台总入口，帮助用户创建或进入合适的项目、群聊和 Agent。
2. **小有（项目管家）**是群聊中的常驻队长，负责需求澄清、任务树拆解、角色匹配、进度追踪、阻塞升级、验收收口与归档。
3. **普通 Agent**承担具体工作，可从模板快速招聘、自定义创建或本地接入。

这里最重要的设计是“小有不是决策者”。官方文档明确规定，重指派、范围裁剪、降级暂缓、验收通过等影响权责和承诺的操作必须由人拍板。这一约束减少了多 Agent 系统在企业环境中“自动运行但责任不清”的风险。

## 5. 核心能力拆解

### 5.1 Agent 创建与接入

- **快速招聘：**从成熟角色模板创建，预填名称、职责与技能。
- **自定义创建：**选择运行引擎、定义工作职责并装配技能；当前文档明确列出 Claude Code 或 OpenClaw。
- **本地接入：**平台生成带 60 秒有效 Token 的连接命令，在本地运行后识别并接入 Agent。本地终端关闭或机器休眠会使其离线。
- **第三方能力：**8 月更新日志显示已接入法律行业 Agent、视频生成 API/MCP 和第三方资产源。
- **协议方向：**9 月 2 日官方公测稿称，已经部署且符合 A2A 协议的 Agent 可接入平台；当前公开使用指南尚未提供完整 A2A 接口规范。

这意味着产品没有把所有执行能力封闭在阿里云自有 Agent 内，而是尝试成为不同 Agent 的协作上层。开放程度的下一步考验，是是否提供稳定、公开、可版本化的 Agent 接入协议，而不只是控制台连接命令。

### 5.2 项目与多 Agent 协作

- 项目空间统一管理成员、群聊和资产。
- 一个群聊对应一个具体任务，小有自动加入且不可移除。
- 用户可在群聊中同时 @ 多个人或 Agent，也可以不指定对象，由小有进行路由。
- 任务过程支持动态规划；用户对产物提出修改意见后，系统可追加新节点，让对应 Agent 调整。
- 群聊生成和上传的文件自动归档，减少跨会话复制上下文。

从产品逻辑看，这比“多个 Agent 各说一段话”更接近项目执行；但公开文档还未证明它已经具备成熟项目管理工具的依赖图、工期、看板、跨项目资源和通知体系。

### 5.3 Skill、知识与资产

Skill 被定义为装在 Agent 身上的“领域 SOP 手册”，按匹配场景加载。资产库分为协作资产和个人知识库，协作资产再按会话和项目归档。当前知识库存储的限时额度为 2GB，单次最多上传 10 个文件。

产品的长期价值取决于能否把“任务结果”进一步结构化为可检索、可评估、可继承的组织经验。目前已具备文件沉淀和项目归档的基础，但版本管理、血缘、权限继承、过期策略与知识质量评估尚未公开。

### 5.4 权限与人在回路

外部服务采用 OAuth 授权。Agent 以任务发起者身份访问外部文档，同时校验平台授权和用户对目标资源的原生权限；任何一层失败都会暂停并提示。当前 OAuth 每次授权有效期 7 天，且仅对企业账号生效。

项目层存在项目管理员和普通成员；群聊中发言、上传文件和邀请人员较开放，添加 Agent、停止任务、删除群聊的权限更受限。受邀协作者不能修改 Agent 配置，调用产生的模型费用计入账号所有者。

这是一个可用的公测级权限骨架，但距离大型企业治理仍有差距：公开文档没有完整说明 SSO/SCIM、细粒度 RBAC、审计导出、数据保留、密钥托管、地域与专有部署。

## 6. 典型用户旅程

以“新产品发布调研”为例：

1. 负责人创建项目空间，加入研究、产品、技术和编辑 Agent。
2. 为本次发布建立群聊，给出目标、范围、截止时间和验收标准。
3. 小有补齐缺失信息，生成包含依赖关系的任务树；人确认后进入执行。
4. 不同 Agent 分别完成官方资料核验、功能拆解、竞品比较和报告撰写。
5. 用户在群聊中查看进度，对关键假设、范围变化和最终验收做决定。
6. 报告、资料和中间产物自动进入项目资产；下次同类调研可复用 Skill、Agent 配置和历史资料。

这个旅程的价值在于降低多 Agent 的“编排税”：普通业务用户不必自己维护每个对话的上下文、交接格式和文件位置。风险则是，若任务路由和状态判断不稳定，小有会成为新的瓶颈或产生“看似在推进、实际难验收”的自动化幻觉。

## 7. 计费、开放条件与商业模式

当前采用积分制，**100 积分对应 1 元人民币计费金额**。公开充值档位为 100 元/10,000 积分、1,000 元/100,000 积分和 10,000 元/1,000,000 积分；充值积分有效期一年。注册体验金为 3,000 积分，当前每日另有 2,000 限时积分。公开上限包括最多 30 个云端 Agent、本地 Agent 接入不限和 2GB 知识库存储。

需要特别注意：同一官方计费页前部称“当前只对模型调用计费，Skill 和 MCP 暂不计费”，后部却列出付费工具与沙箱运行消耗。最合理的解释是文档正在从体验期向更完整资源计费迁移，但在官方修订或控制台实测前，不能把工具与沙箱免费视为稳定承诺。

企业版已确认采用“企业订阅套餐 + 席位”方式，由管理员购买后配置成员、企业 AI 资源和公共知识库；但套餐价格、席位单价、与模型积分的叠加关系尚未公开。商业模式目前以模型/资源消耗和企业订阅为主，未来可能叠加第三方能力市场和私有化方案，后两项仍属分析推断。

## 8. 竞品与差异化

### 竞争关系

| 产品 | 更接近的品类 | 相对万有无界的特点 |
| --- | --- | --- |
| 腾讯 WorkBuddy 本体 | AI 办公与多 Agent 工作台 | 本地文件、桌面端、云端任务和多渠道触达更强；协作结构与资产沉淀是直接交叉点 |
| 扣子 | 职场 AI + Agent/工作流开发平台 | 技能商店、开发部署和生态成熟度更突出；万有无界更强调项目群聊与固定角色协作 |
| Microsoft Copilot Studio / Microsoft 365 Copilot | 企业 Agent 构建与办公生态 | 连接器、身份、治理和 Office 分发更成熟；万有无界的本地 Agent 接入与轻量协作路径更灵活 |
| Asana AI Teammates | 人与 Agent 项目协作系统 | 任务、责任、计划和企业工作管理语义更强，是“人机团队操作系统”方向的重要国际参照 |

**分析判断：**万有无界当前最清晰的产品差异不是模型，而是“多 Agent 项目协作协议”。如果它能把职责、依赖、审批、资产和复用做深，就可能形成高于通用聊天工具的迁移成本；如果只停留在群聊加多个角色，差异会很快被 WorkBuddy、扣子或现有协作软件复制。

## 9. 优势、风险与未知项

### 主要优势

- 对企业多 Agent 落地的真实痛点定义准确：协作、责任、交接、验收和沉淀。
- 小有的能力边界清晰，重要权责决策保留人工确认。
- 云端、自定义、本地和第三方 Agent 的来源较开放。
- 项目资产自动归档，有机会把一次性生成升级为组织经验复用。
- 背靠千问模型、MCP 市场及阿里云企业服务生态，未来整合空间大。

### 主要风险

- 公测期能力与企业级宣传之间存在证据差距，组织治理是否完整仍待验证。
- 多 Agent 会放大 Token、沙箱和工具成本；当前计费文档口径还不够稳定。
- 多 Agent 不天然带来更好结果，路由错误、上下文漂移和责任重复会增加验收成本。
- OAuth 仅企业账号可用且 7 天需重新授权，可能影响高频自动化体验。
- 资产库若缺少版本、权限继承、血缘和质量治理，长期可能演变为新的文件堆积区。
- 尚未看到公开 API、SLA、私有化和标准化第三方 Agent 协议，平台化程度有限。

## 11. 综合判断与建议

万有无界代表了一个值得持续跟踪的方向：**Agent 产品的下一层竞争不是让一个模型更像“万能员工”，而是建立多人、多 Agent 共同工作的组织协议。**阿里从项目空间、群聊、小有和资产库切入，路线比单纯 Agent Builder 更靠近企业日常执行。

建议企业以一个边界清晰、结果可人工验收、数据敏感度较低的流程做 2—4 周试点，例如公开资料调研、内容生产或内部知识整理。评估时不要只看最终文本质量，应记录任务一次完成率、人工澄清轮数、人工返工时间、单位任务积分、权限中断次数、资产复用率和跨 Agent 交接失败率。

## 12. 后续追踪清单

- 企业管理后台的组织、资源、知识、账单、审计和数据大盘是否正式开放。
- 是否发布统一的 Agent 接入协议、开放 API、SDK 或 A2A 兼容能力。
- 计费页面是否统一模型、MCP/工具和沙箱的收费口径。
- SSO/SCIM、审计导出、数据保留、地域、私有化与 SLA 是否补齐。
- Agent 模板和 Skill 市场的数量、质量、审核、版本和商业分成机制。
- 多 Agent 任务的评测、Trace、失败恢复和成本预算控制能力。
- 公测后正式商用时间、价格及现有资产迁移政策。
